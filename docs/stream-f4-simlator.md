# OOOI Events Simulator (F4 Stream)

This component acts as the **producer** in VuelaData's event-driven architecture. Its main job is to create synthetic OOOI events for commercial flights and send them asynchronously to a message broker (RabbitMQ).

This module is designed to test how well downstream consumer systems (APIs and ETL pipelines) handle time changes, message bursts, and operationally incorrect data.

---

## 1. Microservice Architecture

To keep the test environment separate and avoid depending on the main transactional database, this module works in memory and uses the following components:

- **Data Generator (`src/oooi_generator.py`):** The logic engine. It simulates a flight schedule in real time (UTC) and calculates the time differences for takeoff and landing.
- **Producer (`src/producer.py`):** The AMQP client. It converts the generated Python dictionaries into JSON payloads and publishes them to the persistent RabbitMQ queue `eventos_oooi_queue`.
- **Message Broker:** The RabbitMQ Docker container (`rabbitmq:3-management-alpine`). It separates message publishing from message receiving and helps keep events available if the consumer stops.
- **Validation Consumer (`tools/dummy_consumer.py`):** A tool used to check the results. It listens to the queue and prints events in the console. It confirms that messages were processed (ACK), allowing the broker to remove them from the queue.

---

## 2. The OOOI Life Cycle

The simulation follows the standard order of commercial aviation events and calculates each time based on the previous event:

1. **OUT (Off-block):** Calculated from the scheduled departure time, with random changes between -10 and +45 minutes.
2. **OFF (Takeoff):** Generated 10 to 20 minutes after OUT, to represent taxiing to the runway.
3. **ON (Landing):** Generated after the flight time, between 40 and 180 minutes after OFF.
4. **IN (In-block):** Generated 5 to 15 minutes after ON, to represent taxiing to the gate.

---

## 3. Data Contract (JSON Payload)

All messages sent to RabbitMQ follow this contract, so the consumer knows which data types to expect:

```json
{
  "id_externo_evento": "a1b2c3d4-e5f6-7890-1234-56789abcdef0",
  "id_vuelo": 1,
  "numero_vuelo": "VU-1001",
  "codigo_evento": "OUT",
  "fecha_hora_evento_utc": "2026-10-14T07:15:00+00:00",
  "codigo_causa_original": "TECNICA"
}
```

### Field Reference

| Field | Type | Description |
|---|---|---|
| `id_externo_evento` | `UUID v4` | Unique ID for the message generated by the aircraft sensor. |
| `id_vuelo` | `Integer` | Foreign key that links the event to the transactional catalog. |
| `numero_vuelo` | `String` | Commercial flight code, for example `VU-1001`. |
| `codigo_evento` | `String` | Recorded operation stage: `OUT`, `OFF`, `ON`, or `IN`. |
| `fecha_hora_evento_utc` | `String (ISO 8601)` | Exact event timestamp, always using UTC (`+00:00`). |
| `codigo_causa_original` | `String` / `Null` | If the `OUT` event is more than 15 minutes late, it records the original cause (`TECNICA`, `CLIMA`, etc.). Otherwise, the value is `Null`. |

---

## 4. Chaos Engineering (HU-05)

To test data quality rules, `oooi_generator.py` includes a defect injection function that affects exactly **10%** of simulated flights.

The system randomly selects one of these abnormal cases to test the final consumer's data quality filters:

1. **Missing Event (`FALTA_EVENTO`):** Simulates a sensor signal loss. The aircraft records takeoff (`OFF`) and gate arrival (`IN`), but the landing event (`ON`) is never generated or sent to the queue.
2. **Cause Not in the Catalog (`CAUSA_INVALIDA`):** The system replaces a valid delay cause (for example, `CLIMA`) with `ERROR_99`. The receiving database must handle a value that does not exist in its reference table.
3. **Time Paradox (`PARADOJA_TIEMPO`):** Simulates an incorrect time zone setting across midnight. The script takes the `IN` event and subtracts 24 hours, so the database receives a gate arrival time that is earlier than the takeoff time.
